# T3 Code 서버 Go 포팅 계획

기준: 업스트림 `pingdotgg/t3code` v0.1.11 (YATT가 번들하는 버전), 2026-11-25 작성.
이전 조사: 프로젝트 파일 `research/yat3-go-port-scope.md`.

## 1. 목표와 전제

T3 Code 서버(`apps/server`, TypeScript/Effect, 약 33만 줄)를 Go로 다시 구현하고, 최종적으로는 모든 기능을 갖추는 것이 목표입니다. 규모와 업스트림 변경 속도를 고려하면 업스트림 코드를 파일 단위로 옮기는 방식은 끝까지 유지할 수 없습니다. 그래서 이 저장소는 업스트림의 **관찰 가능한 동작**을 스펙으로 고정하고, Go 서버가 그 스펙을 통과하는지를 기계적으로 확인하는 방식으로 진행합니다.

## 2. 방법론: 스펙 → 시나리오 → 구현

```
upstream contracts ──extract.ts──▶ spec/generated/rpc.json ─┐
                                                            ├─▶ t3conform ─▶ 스키마 위반, 골든과의 차이
upstream t3 바이너리 ──record──▶ conformance/golden/*.json ─┘        ▲
                                                                    │
spec/behavior/*.md (규칙 + 시나리오 연결) ─▶ conformance/scenarios ──┘
                                              yatt-server ──check──┘
```

1. **계약 스펙(자동)**: `tools/spec-extract`가 업스트림 `WsRpcGroup`의 Effect Schema를 JSON Schema로 변환합니다. v0.1.11에서 RPC 235개, 공유 정의 860개가 나옵니다. 사람이 쓰지 않으므로 업스트림과 어긋날 일이 없습니다.
2. **동작 스펙(수동)**: 스키마로 표현되지 않는 규칙(어떤 명령이 어떤 스트림 값을 만드는지, 시퀀스 규칙, 오류 형태)은 `spec/behavior/`에 번호를 붙여 씁니다. 규칙마다 검증하는 시나리오를 연결합니다.
3. **적합성 시나리오(언어 중립)**: `conformance/scenarios/*.json`은 서버 구현과 무관한 JSON 파일입니다. 요청을 보내고, 스트림에서 특정 값을 기다리고, 스트림을 끊는 단계로 구성됩니다. `t3conform`이 같은 시나리오를 업스트림 `t3`와 `yatt-server`에 똑같이 실행합니다.
4. **골든 기록**: 업스트림 `t3` 바이너리를 임시 데이터 폴더로 띄워서 시나리오를 실행하고, UUID, 시각, 경로, fiber id처럼 실행마다 달라지는 값을 자리 표시자로 바꾼 기록을 저장합니다. 업스트림을 같은 골든에 다시 실행하면 통과해야 하며, CI가 이것을 매번 확인합니다(기록 자체의 안정성 검증).
5. **이중 검증**: 러너는 골든과 비교하는 것과 별개로, 서버가 보낸 모든 값과 시나리오가 보낸 모든 payload를 `rpc.json`으로 검증합니다. 시나리오를 처음 작성할 때 `thread.visit`에 필수 필드 `visitedAt`이 빠진 것을 이 검증이 바로 잡아냈습니다.
6. **래칫(ratchet)**: `conformance/expected-failures.txt`에 Go 서버가 아직 통과하지 못하는 시나리오를 적습니다. CI는 목록 밖의 시나리오가 실패하거나, 목록 안의 시나리오가 통과하면 실패합니다. 따라서 목록은 줄어들기만 하고, 회귀가 생기면 바로 드러납니다.

이 방식에서 Go 구현자(사람이든 Claude든)가 읽는 자료는 업스트림 코드 33만 줄이 아니라 해당 단계의 스펙 문서, 스키마, 골든 기록입니다. 업스트림 코드는 규칙을 처음 작성할 때 근거를 확인하는 용도로만 읽습니다.

## 3. 업스트림 추적

업스트림 main을 따라가지 않고 **안정 릴리스 태그**에 고정합니다. 근거는 실측입니다. 같은 추출기로 v0.1.11(11-19 커밋)과 main(11-24)을 비교하면, 5일 사이에 메서드 24개가 추가되었고 기존 235개 중 84개의 스키마가 바뀌었습니다. YATT가 쓰는 `dispatchCommand`, `launchThread`, `subscribeShell`도 모두 바뀐 목록에 있습니다.

새 릴리스가 나오면 다음 순서로 따라갑니다.

1. `scripts/spec-update.sh v0.1.12`: 스펙을 다시 만들고, 추가/삭제/변경된 메서드를 출력합니다(`specdiff`).
2. `scripts/conformance.sh record 0.1.12`: 골든을 다시 기록합니다. 골든의 diff가 곧 동작 변경 목록입니다.
3. `scripts/conformance.sh go`: 새로 실패하는 시나리오가 이번 릴리스에서 해야 할 Go 작업입니다.
4. 이 세 가지를 PR 하나로 묶습니다. 업스트림이 바꾼 규칙은 `spec/behavior/`도 함께 고칩니다.

`Upstream watch` 워크플로가 매주 월요일 최신 nightly와의 차이를 요약해서, 다음 릴리스에서 얼마나 바뀔지 미리 보여 줍니다.

## 4. 데이터 폴더

Go 서버는 기본값으로 `~/.yatt/server`를 쓰고, 업스트림의 `~/.t3`에는 쓰지 않습니다.

- `~/.t3`는 이벤트 소싱 DB이고 마이그레이션이 계속 늘어납니다(0.1.11 기준 102번). 같은 DB에 쓰려면 Go 서버가 업스트림 마이그레이션 헤드를 계속 따라가야 하고, 공식 앱 서버와 동시에 실행되면 데이터가 손상될 수 있습니다.
- 별도 폴더를 쓰면 DB 스키마를 Go 쪽에서 자유롭게 설계할 수 있습니다. 와이어 스펙만 맞추면 되므로 추적 비용이 크게 줄어듭니다.
- 대가로 공식 T3 Code 앱에서 만든 스레드는 Go 서버에서 보이지 않습니다. P3에서 `~/.t3`를 **읽기 전용으로 가져오는** 기능을 만들어 이 부분을 보완합니다.

## 5. 단계

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| P0 (이 PR) | 스펙 추출기, 적합성 러너, 골든 7개, Go 골격(Effect RPC 프레이밍, 토큰 인증, `serve`/`auth session issue` CLI, 환경 정보 엔드포인트), CI | 업스트림이 골든 7/7 통과, Go 서버 5/7 통과 |
| P1 YATT 코어 | SQLite 이벤트 로그와 프로젝션, 셸/스레드 스트림, `projects.mutate`, `dispatchCommand`의 스레드 명령, `launchThread`(프로바이더 호출 제외), `server.getConfig`, `server-runtime.json` 기록, 페어링과 `/oauth/token` | 프로바이더 없이 YATT를 Go 서버에 붙여서 스레드 목록, 생성, 이름 변경, 보관이 동작 |
| P2 프로바이더 | 시나리오용 가짜 프로바이더, Codex(`codex app-server` JSON-RPC, 스키마에서 Go 타입 생성), Claude(`claude` CLI stream-json), 메시지 전송, 대기열, 중지, 제목 생성 | YATT에서 실제 에이전트와 대화. 이 시점에 Go 서버를 번들한 YATT 빌드를 Homebrew로 배포 |
| P3 워크스페이스 | 승인 요청 응답, 첨부, 체크포인트와 diff, 워크트리, git/vcs, 터미널, 파일 시스템, `~/.t3` 가져오기 | `spec/phases.tsv`의 P3 메서드를 모두 구현 |
| P4 나머지 | PR/이슈/소스 컨트롤 연동, MCP, 예약 작업, 미리보기, cloud/relay/peer/device 등 | 모든 메서드 구현. 업스트림 웹 클라이언트를 Go 서버에 붙여도 동작 |

단계별 메서드 수는 `spec/coverage.md`에 자동으로 집계됩니다(P1 15개, P2 19개, P3 90개, P4 111개).

### 프로바이더 시나리오

에이전트 응답은 실행마다 달라서 골든으로 기록할 수 없습니다. P2에서는 `codex`와 `claude` CLI를 흉내 내는 가짜 실행 파일을 `conformance/fixtures/`에 두고, 시나리오가 PATH 앞에 그 폴더를 넣어 서버를 띄웁니다. 가짜 실행 파일은 정해진 입력에 정해진 출력을 내므로, 업스트림과 Go 서버 모두에서 같은 기록이 나옵니다. 프로바이더 어댑터의 동작 차이를 언어와 무관하게 비교하는 수단이기도 합니다.

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 업스트림 변경 속도 | 릴리스 태그에 고정하고, 릴리스마다 스펙 diff와 골든 diff로 작업량을 계산합니다. |
| 스키마가 표현하지 못하는 필드(`{}`로 나오는 선언 타입) | 동작 스펙과 골든 기록으로 보완합니다. 필요하면 추출기에 해당 선언의 JSON 표현을 추가합니다. |
| Claude 프로바이더 | 업스트림은 TypeScript 전용 SDK를 쓰므로 Go에서는 CLI 프로토콜을 직접 구현해야 합니다. 가짜 실행 파일 시나리오로 업스트림 어댑터의 입출력을 먼저 기록하고, 그 기록을 기준으로 구현합니다. |
| 골든 기록의 비결정성 | 업스트림을 같은 골든에 다시 실행하는 CI 단계가 흔들리는 값을 바로 드러냅니다. 정규화 규칙은 `server/internal/conform/normalize.go`에 모읍니다. |
| 규모 | 단계마다 완료 기준을 YATT에서 실제로 쓰는 기능으로 잡아서, 중간 단계에서도 쓸 수 있는 결과물이 나오게 합니다. |

## 7. 배포

P2가 끝나기 전에는 Go 서버를 배포하지 않습니다. CI가 빌드와 적합성 결과만 남깁니다. P2가 끝나면 YATT macOS 앱에 업스트림 서버 대신 Go 서버를 번들하는 빌드를 만들고, 기존 Release 워크플로와 Homebrew cask로 배포합니다.
